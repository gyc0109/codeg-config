## 3. 链路实测（决定整个方案的关键数字）

| 测试 | 结果 |
|---|---|
| 单流 200 MB（`ssh | cat > /dev/null`） | 254 s → **6.3 Mbps** |
| 4 路并发 40 MB | 48.6 s → **6 Mbps** |
| rsync `-z` 实际过网速率 | **911 KB/s ≈ 7.3 Mbps** |

**结论：瓶颈在源端出口（约 6–7 Mbps），并发拉不上去。** 17 G 全量裸传要 6.5 小时。
但文本类数据 rsync 压缩比约 3:1，实际快得多——所以方案围绕"尽量多压缩、少传字节"设计。

## 4. 为什么没有直接用 `migrate-push.sh`

`migrate-push.sh` 只搬**配置**（env、systemd、nginx、证书、dotdir），它：

- 不补系统包（源 1070 个 vs 目标 452 个）
- 不搬 `/usr/lib/node_modules`（4.5 G，所有 agent 的程序）
- 不搬 `/opt/litellm-venv`（663 M）

跑完达不到"一模一样"。所以改成下面的三段式。

## 5. 三段式方案

### 第 1 段：目标机补包（不走慢链路）

```bash
# 源端导出清单
dpkg --get-selections | awk '$2=="install"{print $1}' | LC_ALL=C sort > /tmp/src-pkgs.txt
# 目标端同样导出后取差集，用腾讯云内网镜像装
apt-get install -y --no-install-recommends $(cat need.txt)
```

- 差集 728 个，装 726 个（**故意跳过 2 个**：`grub-cloud-amd64`、`linux-image-6.12.111+deb13-amd64`
  —— 前者会动引导器、后者是源上的旧内核，装了反而有风险）
- 目标机自带 128 个源上没有的包（`cloud-init`、`grub-efi`、内核 headers 等），是腾讯云镜像的基线，**保留不动**
- 结果：源 1070 个包，目标一个不缺

### 第 2 段：rsync 搬数据（`migrate-stage2.sh` 的前身 + 分两批）

批 1 —— `/root` 全量（含所有会话）：

```bash
rsync -aHAX --numeric-ids -z --partial --stats \
  -e 'ssh -o BatchMode=yes' \
  --exclude='.rustup/' --exclude='.cache/' --exclude='.npm/_cacache/' \
  --exclude='.ssh/authorized_keys' --exclude='**/*.sock' \
  /root/ root@TARGET:/root/
```

- 结果：**56,791 个文件 / 3.46 GB，过网 1.16 GB，21 分钟，删除 0 个**
- 排除 `.rustup`（1.5 G，没在用的 Rust 工具链）
- **必须排除 `.ssh/authorized_keys`**：否则源端的文件会覆盖掉目标端的，把自己的登录钥匙干掉

批 2 —— 见 `migrate-stage2.sh`：密钥 / systemd / nginx / 证书 / `/usr/local` / `/opt` / `/var/www` / docker / `node_modules`。

- `/usr/lib/node_modules` 4.5 G，压缩后仍慢（含 esbuild、tree-sitter 等压不动的 `.node`），跑 1.35 MB/s，约 30 分钟

### 第 3 段：目标机收尾（`migrate-stage3.sh`）

权限、软链、swap、临时 HTTP 站点、启服务、自检。

## 6. 迁移中踩到的坑（都是必然踩的，记下来）

### 6.1 目标机 DNS 是坏的
腾讯云镜像的 `/etc/resolv.conf` 指向 systemd-resolved 的 stub（127.0.0.53），但 resolved **没有上游**。
表现：litellm 启动时拉模型价格表 `Temporary failure in name resolution`，apt 更新报
`No address associated with hostname`。

修复（`/etc/systemd/resolved.conf`）：

```ini
[Resolve]
DNS=183.60.83.19 183.60.82.18
FallbackDNS=8.8.8.8 223.5.5.5 119.29.29.29
```

⚠️ **`183.60.83.19` 不能省**：`mirrors.tencentyun.com` 解析到 `169.254.0.3`（内网地址），
只有腾讯云内网 DNS 能解出来。只写 8.8.8.8 / 223.5.5.5 的话 apt 直接废掉（我第一次就踩了）。

### 6.2 nginx 的 default 站点抢 default_server
目标机装上 nginx 后自带 `sites-enabled/default`（`listen 80 default_server`），
和临时 HTTP 站点冲突：`a duplicate default server for 0.0.0.0:80`。

修复：`rm -f /etc/nginx/sites-enabled/default`。

### 6.3 node 版本必须先对齐再装 node_modules
apt 补包时 `nodejs` 从 Debian 源装成了 **20.19.2**，而源端是 nodesource 的 **24.21.0**。
`/usr/lib/node_modules` 已经按 node 24 落盘，用 node 20 跑必然炸。

修复：等 `nodesource.list` + keyring 到位后再装，并**钉死版本**：

```bash
apt-get install -y --allow-downgrades nodejs=24.21.0-1nodesource1
```

（`node_24.x` 源里现在是 24.22.2，不钉版本就漂了。）

### 6.4 swap 必须有
源端 3921 MB 已用满且**没有 swap**（有 OOM 记录）。目标 3665 MB 更小，不建 swap 一上量就 OOM。
`migrate-stage3.sh` 建 2 G `/swapfile` + `vm.swappiness=10`。

### 6.6 在新机器上跑 agent 冒烟测试，会污染 agent 的 dotdir

迁移完在新机器上跑了一轮 10 个 agent 的 PONG 测试（`/root/codeg-work/fulltest.sh`）。
agent 一启动就会重写自己目录下的状态文件：

```
.cline/cli-node-extra-ca-certs.pem  内容不变，mtime 被改成"现在"
.codex/.tmp/plugins*                 codex 启动时拉插件市场，目标机多出 15,642 个文件（228M）
.kimi-code/、.codebuddy/、.claude/sessions/ …  各多出 7–17 个新 session 文件
```

后果：下一次 rsync 会看到 1,500+ 个"时间不同"的文件全部重传一遍（内容其实一样），
白白多花 20 分钟。**所以收尾必须带 `--delete` 把这批测试痕迹清掉**，否则新机器比旧机器"多"东西。

正确的顺序是：**先同步 → 再测 agent → 再 `--delete` 清理 → 再同步**。
或者干脆测完机器重建。

### 6.7 `/usr/local/bin/go`、`gofmt` 在源上是软链，在目标上被装成了普通文件

源：`/usr/local/bin/go -> /usr/local/go/bin/go`（软链）
目标：`/usr/local/bin/go` 是一个 17 MB 的普通文件

rsync 报 `could not make way for new symlink: go` + `cannot delete non-empty directory: go`（rc=23）。
收尾时要先删掉目标上的普通文件，让 rsync 重新建软链。

### 6.8 nginx 反代必须保留 WebSocket 的 upgrade 头

CodeG 前端靠 `/ws/events` 这条 WebSocket 维持连接，断线时页面显示
"Connection lost / Trying to reconnect to the server"。

重装后我手写的 `codeg-ip` 站点最初带了一套自定义头：

```nginx
proxy_set_header Upgrade    $http_upgrade;
proxy_set_header Connection "upgrade";      # ← 无条件发送
```

结果普通 `POST /api/*` 全部返回 404（`Connection: upgrade` 却带空的 `Upgrade` 头，
上游按非法升级请求处理）。为了修 404，我把整个头块删掉只留 `proxy_pass`——
API 通了，但 **WebSocket 全挂**，`/ws/events` 返回 400。

正确写法是用 `map`，只在客户端真的要升级时才发 upgrade：

```nginx
# /etc/nginx/conf.d/websocket-upgrade.conf（map 必须在 http 块内）
map $http_upgrade $connection_upgrade {
    default upgrade;
    ''      close;
}

# server 块
proxy_http_version 1.1;
proxy_set_header Upgrade    $http_upgrade;
proxy_set_header Connection $connection_upgrade;
proxy_buffering    off;
proxy_read_timeout 3600s;
proxy_send_timeout 3600s;
```

修好后 `GET /ws/events` 返回 **101**（协议升级成功），页面恢复正常。

**判断口诀**：`400` = 卡在 nginx 头没传对；`401` = 已经到应用层，只是没带 token。

### 6.5 codeg.db 是 WAL
直接 `rsync` 或 `cp` 拿到的是**撕裂快照**。必须：

```bash
sqlite3 /root/.local/share/codeg/codeg.db ".backup '/path/snapshot.db'"
```

最终增量同步前要停 codeg（见 §9）。

## 12. 事故：收尾脚本把目标机的根目录清空了（17:26）

这一段必须写下来，它是这次迁移最重要的教训。

### 12.1 发生了什么

收尾脚本 `migrate-finalize.sh` 里的 `push()` 函数，用「源路径的父目录」来推目标路径：

```bash
rsync -aHAX ... --delete "$src" "$TARGET:$(dirname "$src")/"
```

对 `src=/root/` 来说，`dirname /root/` 的结果是 **`/`**。于是这条命令实际变成了：

```
rsync --delete /root/  root@150.109.241.115:/
```

`--delete` 会删掉目标端所有源端没有的东西——`/bin`、`/sbin`、`/usr`、`/etc`、`/var`、`/lib` 全部被清空。
命令跑了 **36 秒**后被手动终止，删到一半，留下一个不可引导的系统。

日志里那行目标路径是 `root@150.109.241.115://`，**多出来的斜杠就是信号，当时没抓住**。

### 12.2 为什么当时没立刻发现

系统文件被删光了，但**已在运行的进程不受影响**，所以现场表现很迷惑：

| 现象 | 真实原因 |
|---|---|
| nginx 还在响应，但 `GET /` 返回 404 | nginx 进程在内存里活着，但 `/var/www` 没了 |
| codeg API 返回 200 但会话是 `[]` | codeg 活着，但 `codeg.db` 被删，SQLite 就地新建了空库 |
| SSH 能建连但立刻断开、不发 banner | sshd 进程活着，但 `/bin/sh`、PAM 没了，认证做不下去 |
| 重启后反复重启 | `/sbin/init` 不存在，内核 panic，`panic=` 参数触发自动重启 |

`run-init: can't execute '/sbin/init': No such file or directory` 这条就是最终定论。

### 12.3 修复方式

目标机是当天新买的、没有任何独有数据，源机完好。所以直接**从控制台重装系统**，重新迁移。
`fsck` 报 `clean` 说明文件系统本身没坏，只是文件不见了——这种状态没有就地修复的办法。

### 12.4 改了什么（现在的 `push()`）

```bash
push(){ local src="$1"; shift
  local dst="${src%/}"                       # /root/ -> /root
  case "$dst" in ""|"/"|"//") say "!!! 拒绝：目标解析为根目录"; return 1;; esac
  rsync -aHAX --numeric-ids -z --partial --delete --itemize-changes \
    -e "$SSHOPT" "$@" "$src" "$TARGET:$dst/"      # 目标路径 == 源路径
}
```

两条：**目标路径不再推算，直接用源路径本身**；**解析成 `/` 就拒绝执行**。

### 12.5 另外三条纪律

1. **`--delete` 之前必须干跑**：`rsync -n --delete --itemize-changes` 把删除清单拉出来逐条看，确认没有系统文件才真跑。
2. **`"${SSH[@]}"` 不是 `"${SSHOPT}"`**：把 `ssh -o ...` 存成字符串再整体加引号，会被当成一个命令名执行（`command not found`）。这个错误在 `migrate-finalize.sh` 和 `verify-v2.sh` 里**各犯过一次**，两次都导致后续步骤静默失效。
3. **校验脚本必须检查 rsync 的退出码**：只 `grep -c` 输出行数的话，连接失败时结果是"0 差异"，看起来完美，实际什么都没比。

### 17.2 trae —— 官网那条命令在这台机器上是 403

文档给的：

```bash

```

从首尔这台机器访问 **`trae.cn` 直接 403**（Apache 403，225 字节）；

换浏览器 UA、加 Referer/Sec-Fetch 全套头都没用 —— 是 CDN 侧的地域/风控拦截，不是缺头。

真正的源在同域 CDN 上，路径一样：

```

```

装了 **TRAE CLI 0.213.1**。下载包在 `.../trae-cli/v2/releases/<版本>/traex-linux-x86_64.gz`，
有几百 MB，前台跑会被 600s 超时打断，**要放后台**。

> 没有走 `curl | sh`：先下载到本地读完再执行。查过脚本里没有 `eval`、
> `base64 -d`、二次管道执行，装到 `$HOME/.local/bin`，不需要 sudo。
> 它会顺带装 bubblewrap 到 `~/.local/bin/bwrap`，并往 `~/.zshrc` 追加一行 PATH。

**装完必须补软链**，否则 codeg 认不出来：

```bash
for n in traecli trae-cli coco ta; do
  ln -sfn "/root/.local/bin/$n" "/usr/local/bin/$n"
done
```

原因：安装器装到 `~/.local/bin`，而 **codeg 服务用的是 systemd 默认 PATH**
（`/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin`），不含 `~/.local/bin`。
kiro 早就是这么处理的（`/usr/local/bin/kiro-cli -> /root/.local/bin/kiro-cli`）。

> **通用教训：任何装到 `~/.local/bin` 的 CLI，都要补一条 `/usr/local/bin` 软链，
> 否则 codeg 里永远是"未安装"。** 这和 §16.1 漏搬 `/usr/bin` 软链是同一类问题。

登录：`traecli login` 是 **回调式** SSO，起一个 `http://localhost:<port>` 本地服务，

所以要按它提示的第二种方式：在别的机器上登录完，**把最后那个 127.0.0.1 回调 URL
复制回终端粘贴**。或者用 ToB PAT：

```bash
export TRAECLI_PERSONAL_ACCESS_TOKEN=<token>
traecli login --with-trae-pat
```

```bash
codeg-cli --url http://127.0.0.1:3080 --token "$CODEG_TOKEN" \
  agents install open_code  --version 2.2.5 --wait 600
codeg-cli --url http://127.0.0.1:3080 --token "$CODEG_TOKEN" \
  agents install antigravity --version 1.4.5 --wait 900
```

**旧版本目录会被自动删掉**，不用手动清 `acp-binaries`。两个都端到端复验通过。

### 18.2 ZCode：adapter 有、官方运行时没有

ZCode 这个 agent 是**两层**：

- `zcode-acp-server@0.82.0`（npm，ACP 桥接器）—— 有
- **官方 ZCode 客户端的 `zcode.cjs`**（真正干活的那个）—— 一直没有

桥接器的解析顺序：`ZCODE_BIN` → PATH 上的 `zcode` → 桌面版安装目录。
`find / -name zcode.cjs` 全盘为空，所以这个 agent **从迁过来就没通过**，不是这次升级弄坏的。

官方 Linux 版在 `zcode.z.ai`（最新 3.17.2，AppImage 247MB）：

```
https://cdn-zcode.z.ai/zcode/electron/releases/3.17.2/linux-x64/ZCode-3.17.2-linux-x64.AppImage
```

不需要 GUI，也不需要 FUSE —— 直接解包：

```bash
cd /root/zcode-app
curl -fL -o ZCode.AppImage "<上面的 URL>"
chmod +x ZCode.AppImage
./ZCode.AppImage --appimage-extract        # 得到 squashfs-root/
```

**只需要搬 `resources/glm` 和 `resources/config` 两个目录**，`app.asar` 有 390MB 不用管：

```bash
mkdir -p /opt/ZCode/resources
cp -a squashfs-root/resources/glm squashfs-root/resources/config /opt/ZCode/resources/
```

`/opt/ZCode/resources/glm/zcode.cjs` 正好是桥接器自动发现的三个候选路径之一，不用设 `ZCODE_BIN`。
**`resources/config/provider/zcode-builtin.json` 必须一起搬** —— 桥接器是从
`<entryDir>/../config/provider/` 推这个文件的（见 `resolve.js` 的
`BUILTIN_PROVIDER_ENV` 注释）。只搬 `glm/` 会踩 README 里记的那个坑：
CLI 启动即报 `无法定位 CLI ZCode Built-in Provider Config`，1 秒内 exit 1。

装完 `/opt/ZCode` 占 130M。

### 18.3 还没做的两步

1. **登录**：不用装桌面版。桥接器自带 `zcode-acp setup --provider zai|bigmodel`，
   交互式隐藏输入，把 GLM Coding Plan 的 key 存进 `~/.zcode/v2/config.json`。
   （桌面版也会生成这个文件，但服务器上没 GUI，走 setup 更实际。）
2. **验证**：`node /opt/ZCode/resources/glm/zcode.cjs --version` 能打印 `0.17.1`，
   但真正起来还要 codeg 里跑一次 `--agent zcode` 才算数。

> 已知佐证：解包后单独跑 `--version` 输出 `0.17.1`，说明文件本身可用。

### 18.6 单独跑 CLI 必须手动补 provider 环境变量

直接 `node zcode.cjs login zai` 会报：

```
无法定位 CLI ZCode Built-in Provider Config：
  /opt/ZCode/resources/glm/provider/zcode-builtin.json,
  /config/provider/zcode-builtin.json
```

它自己的查找逻辑只看 `<entryDir>/provider/` 和 `<entryDir>/../../../config/provider/`
（从 `glm/` 往上五级跑到了 `/config`，是给 monorepo 源码树用的）。

**codeg 走桥接器时不会有这个问题** —— 桥接器的 `resolve.js` 会自己算好并注入：

```bash
export ZCODE_BUILTIN_PROVIDER_CONFIG_FILE=/opt/ZCode/resources/config/provider/zcode-builtin.json
export ZCODE_PERSONAL_PROVIDER_CONFIG_FILE=/root/.zcode/v2/provider_config.json
```

（builtin 取 `<entryDir>/../config/provider/zcode-builtin.json`；personal 固定是
`~/.zcode/v2/provider_config.json`。两个都要设，只设 builtin 会触发 CLI 自己去
re-sync 一份 runtime 副本，后面 account-config push 的 revision 对不上，
表现为所有模型都答 "Provider Registry 中不存在 Model"。）

### 18.7 登录

`zcode login zai` 是**远程回调**式，不是 localhost：

```
https://chat.z.ai/api/oauth/authorize?...&redirect_uri=https://zcode.z.ai/api/v1/oauth/cli/callback/zai&state=<state>
```

回调打在 zcode.z.ai 上，CLI 这边轮询 state，所以**在自己电脑的浏览器里打开这个 URL 授权即可**，
不需要端口转发。授权后凭据落到 `~/.zcode/v2/config.json`。

前提：这个 Z.AI 账号得开通过 GLM Coding Plan，否则模型列表还是空的。
